# 작품·판본 모델 검토

검토 기준: `feature/library-studio`, `79f7dd70`의 `studio/store.py`, `sources.py`, `server.py`와 기존 테스트. 현재 체크아웃의 파일을 읽어 확인했으며 기존 DB는 열지 않았다.

## 현재 모델

`works`는 `lrr_id UNIQUE`, 페이지 수, 바이트 수, 읽기 진도를 갖는다. `sources`가 `work_id`를 직접 참조하고 `(provider, external_id)`를 전역 고유 키로 사용한다. `sync_lrr`는 아카이브 ID로 작품을 찾는다. 별도의 판본 모델은 없다. 따라서 현재 work는 추상적인 원작보다 개별 만화 아카이브에 가깝다.

출처 충돌을 거부하고 제목·번호로 자동 병합하지 않는 기존 동작은 적절하다. 다만 한 work에 여러 출처를 붙이면 서로 같은 판본인지, 번역·각색·음성화인지 표현할 수 없다. 원본 메타데이터 전체를 보존하는 이력 테이블도 없다. 출처의 태그·댓글은 현재 값으로 갱신된다.

## 파생 서비스 모델

| 엔터티 | 의미 | 연결/고유성 |
| --- | --- | --- |
| works | 사용자가 지정한 원작 묶음 | 로컬 UUID. 제목은 고유하지 않음 |
| editions | 만화, 번역본, 보이스코믹, 음성판 | 명시적으로 선택한 work_id에 연결. 각각 별도 UUID·언어·제작진 |
| sources | 특정 판본의 출처 정체성 | `(provider, external_id)` 고유. 다른 판본에 재사용하면 거부 |
| source_snapshots | 제출한 URL·원본 JSON·기록 시각 | 추가만 수행. 같은 출처의 변경도 새 기록으로 보존 |
| tracks | 음성판/보이스코믹의 개별 파일 | 판본 내 순서·상대 경로 고유. 길이·이어듣기 초 단위 |

제목·번호·언어·태그 유사성에 의한 자동 연결은 없다. 서로 다른 출처의 같은 번호는 별개의 정체성이다. 출처 ID는 문자열 그대로 보존하며 출처 이름은 소문자 namespace로 명시 입력한다. 예를 들어 사이트가 번호를 여러 카탈로그에서 재사용한다면 `site.catalog`처럼 분리해야 한다. URL에서 ID를 추측하거나 사이트 사이의 동등성을 판단하지 않는다. 출처 이름·ID·URL의 일치 여부는 현재 수동 입력자가 확인한다.

같은 원작의 만화·번역본·음성판은 **서로 다른 edition**으로 생성한다. 같은 출처 ID가 실제로 여러 판본을 포괄하는 번들일 경우 현재 모델은 한 판본에만 소유를 허용한다. 번들 하위 항목 모델은 향후 별도 설계가 필요하며 임의 접미사로 ID를 변조하지 않는다.

## 음성·영상·번역 자막 확장

`work_codes`는 사용자가 확인한 DLsite RJ 코드를 원작 묶음에 연결한다. `(provider,code)`가 다른 원작에 있으면 거부한다. 이 분류는 특정 판본의 출처 정체성과 다르며, 같은 RJ 작품의 보유 파일 버전들이 하나의 원작 아래 있을 수 있도록 한다. 기존 `sources`와 원본 메타데이터 이력은 그대로 보존한다. 번호·제목 일치에 의한 자동 연결은 추가하지 않았다.

`edition_profiles`에서 음성/영상과 번역 없음/별도 번역 자막/자막 합성 영상을 분리한다. 파일 확장자나 자막 파일 존재만 보고 번역 여부를 자동 추측하지 않는다. `subtitles`는 특정 트랙의 SRT/WebVTT 파일·언어·이름을 연결한다. `tracks.position`은 판본 내 사용자 재생 순서이며 순서 저장은 모든 트랙의 정확한 순열만 허용하는 단일 트랜잭션이다. 재생 위치·출처·원본 파일은 순서 변경으로 바뀌지 않는다.

기존 음성 전용 DB는 별도 보관 후 추가 테이블만 생성한다. 만화 모델·DB·NAS에는 이 확장을 적용하지 않는다.

## 분리와 향후 연동

별도 worktree/브랜치, `audio-studio/` 소스, `audio-studio/data/audio.sqlite3`, loopback 43130을 사용한다. 만화의 `.env`, DB, Redis, LANraragi API 및 NAS를 참조하지 않는다. 기존 Studio DB의 자동 마이그레이션·동기화는 없다. 서비스가 다른 종류의 기존 DB를 열려고 하면 쓰기 전에 거부한다.

향후 만화 가져오기는 별도 검토 대상이다. 원본을 읽기 전용으로 내보낸 뒤 기존 work를 개별 만화 판본으로 취급하고 legacy ID와 원본 출처 데이터를 보존해야 한다. 원작 묶음은 사용자 확인으로 만들어야 하며 이 구현에서는 가져오기나 기존 데이터 변경을 수행하지 않는다.
