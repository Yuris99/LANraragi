# Catalog preservation before copy removal

A copy-review count is a count of page-matching **pairs**, not necessarily a count of distinct duplicate files. `plan-copy-cleanup.py` consumes the existing private review report on the NAS. It does not repeat the complete library scan. It groups copies, holds multiple possible survivors, revalidates full archive SHA256 and every page stream, and maps candidate files to the local catalog using the upstream ID only as a locator. Shared partial IDs are held rather than merged. Original basenames and full upload records must agree; synchronize Studio first when basename evidence is missing.

The new private plan contains both works' source metadata/comments, user tags, favorites, rating, reading position, local numbers and related job records. Worker leases are excluded. Changed files, missing catalog entries, uncertain upload ownership and active download jobs prevent advancement. Extra/non-page metadata remains explicitly listed. SQLite is opened read-only in a consistent query-only transaction; inputs are never written. Only aggregate counts are printed. Reports remain NAS-local and must not be uploaded.

This is an executable planning step, **not cleanup execution**. Neither a successful page match nor a catalog match alone permits deletion. The plan still requires a consistent database backup, preservation of both archives' different metadata, an implemented catalog merge, redirects for old UUID/local-number bookmarks, backend survivor download verification, fresh revalidation and index reconciliation. No deletion, rename, original-folder change, service restart or deployment-controller update occurs. Existing app-only deployment permission does not provide a NAS host execution path.

The separate fixed NAS wrapper runs a disposable network-disabled container with original files, app copies, prior reports and the catalog mounted read-only. Its only write mount is a new dedicated cleanup-plan directory. It validates the existing app image and named volumes and pins downloaded planning sources. NAS-local sudo is necessary to read the two protected storage roots; no credential is sent to cloud.

Validation uses generated ZIP/CBZ archives and a temporary Studio database: pair/copy ambiguity, different non-page metadata, source/comments/tags/rating preservation in the plan, changed candidates, unsynchronized survivors, path traversal rejection and unchanged inputs. Successful synthetic tests are distinct from actual NAS planning, cleanup and live-site evidence.


`plan-nas-copy-cleanup.sh preview|plan <approved NAS root>` is the fixed wrapper. Synchronize Studio first to populate archive basenames. It automatically selects the latest NAS-local `copy-review-*.json`, writes a new private plan under the dedicated `review-reports/cleanup-plans` directory and prints distinct-copy/pair/catalog/hold and preservation counts only. A successful plan does not remove anything.217unit/HTTP/deployment tests passed; actual NAS planning and cleanup remain unverified until operator execution. No app runtime or release generation changes are part of this planning-only update.
