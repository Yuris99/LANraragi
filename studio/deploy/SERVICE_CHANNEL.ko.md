# Studio 서비스 배포 채널

기존 NAS 예약 작업의 `poll.sh tick` 명령을 유지하면서, 앱 코드 외에 별도의
사이트 로그인 서비스와 NAS 다운로드 작업자를 설치·업데이트한다. 사용자가
승인한 Studio 전용 범위 확장이다. NAS SSH 접속 권한이나 다른 프로젝트의
실행기는 사용하지 않는다.

## 한 번 필요한 연결

기존 앱 업데이트 채널은 자신의 호스트 실행기를 교체할 수 없다. 따라서 최초
한 번은 NAS에서 고정 커밋의 `install-service-channel.sh`를 실행해야 한다.
인수는 기존 전용 앱 경로, 검토한 40자리 커밋, 해당 커밋의
`service-controller.sha256` SHA-256, `install`이다. `preview`는 변경하지 않는다.
설치 스크립트와 커밋·해시는 배포 담당자가 함께 제공한다.

실사용 진입점은 고정 커밋의 `enable-service-channel.sh EXISTING_APP_ROOT`이다.
이 스크립트가 위 설치기·매니페스트를 고정 커밋과 해시로 확인한다. 설치 후
업데이트가 활성화돼 있으면 첫 조회를 백그라운드로 시작한다. SSH 창을 닫아도
진행되며 `first_tick=started`는 완료를 뜻하지 않는다. 최초 조회 로그는 컨트롤러
전용 폴더의 `first-services.log`다. 로컬 비활성 설정은 강제로 바꾸지 않는다.

설치기는 기존 컨트롤러·설정 해시와 잠금을 확인하고, 기존 `poll.sh`와 해시를
`before-service-channel`에 보관한다. 기존 앱 실행기는 `poll-app-legacy.sh`로
보존한다. 새 디스패처와 서비스 실행기·파서·레시피 8개 파일을 검증하고
고정한다. 예약 작업, 활성화 여부, NAS 계정·권한·방화벽은 변경하지 않는다.
이미 설치되거나 중단 흔적이 있으면 덮어쓰지 않는다.

이후에는 GitHub의 `nas-services.json`만 게시하면 NAS가 직접 정해진 소스와
의존성을 받아 두 이미지를 순서대로 빌드한다. 큰 이미지 파일을 사용자가
옮길 필요가 없다. 최초 Chromium 빌드는 NAS에서 오래 걸릴 수 있다.
Docker Hub, deb.debian.org, security.debian.org, pypi.org,
files.pythonhosted.org 등 정상 패키지 접근이 필요하다. 정책·인증·TLS 오류는
로그에 남기고 멈추며 미러 전환이나 차단 우회를 하지 않는다.

## 고정 범위와 요청

- 요청은 스키마·활성 여부·증가하는 세대·커밋·작업자 시작 여부·정확히 7개
  소스 파일 해시만 허용한다. 중복 키, 임의 명령·경로·URL·이미지·Compose는 거부한다.
- Dockerfile·Compose·호스트 설치기는 최초 설치 시 고정한다. 소스 요청으로
  호스트 스크립트나 컨테이너 권한을 바꾸지 않는다. 레시피 변경은 별도 로컬 검토가 필요하다.
- 로그인 프로젝트는 기존 Studio 전용 네트워크와 데이터 볼륨을 확인한다.
  초기화기는 새 연결 파일 2개만 만들고, 로그인 키·세션은 전용 새 볼륨에 보관한다.
  Studio·LANraragi 재생성, DB 복사, 기존 미디어·ACL·Stash·NMLO 변경은 없다.
- 브라우저는 비루트·읽기 전용 루트·메모리 1GiB·외부 포트 없음이다.
  작업자는 메모리 384MiB·동시 실행 1·기존 전용 다운로드 경로만 쓴다.
  이미지 빌드는 순차 실행하고 각각 메모리 1GiB로 제한한다. CPU CFS 할당은 사용하지 않는다.
- `worker: true`는 NAS 작업자를 시작/업데이트한다. 대기 중인 명시적 NAS
  외부 엔진 작업이 실행될 수 있다. `false`는 새로 시작하지 않으며 기존 작업자를 중지하지 않는다.
- 기존 앱 릴리스가 성공한 뒤 서비스 경로를 처리한다. 앱 릴리스 실패 시 서비스도 보류한다.
  로컬 `disable`은 두 배포 경로의 새 실행을 중지한다. 실행 중인 서비스나
  진행 중인 작업을 강제 종료하지 않는다.

## 상태와 복구

기존 `poll.sh status`가 앱 상태와 `services` 상태를 함께 보여준다.
서비스 상세 로그는 컨트롤러 전용 폴더의 `services.log`에만 남는다.
`services=healthy`는 로그인 RPC 연결 확인을 뜻한다. 실제 사이트 인증·다운로드
성공이나 브라우저 화면 품질을 뜻하지 않는다. 작업자 기동 결과는 로그 및
Studio의 작업자 연결 표시로 별도 확인한다.

파일 수신 실패는 서비스 변경 전이므로 다음 예약 시 다시 받을 수 있다.
검증된 소스로 빌드를 시작하면 해당 세대를 기록한다. 빌드·설치 실패와 중단은
같은 세대에서 재시도하지 않는다. 로그를 검토하고 수정한 새 세대를 게시한다.
`recover-locks`는 종료된 자신의 PID 잠금만 해제하며 세대 격리를 지우지 않는다.
갑작스러운 전원 차단 시 `in_progress`가 남을 수 있으므로 건강 상태로 해석하지 않는다.

로그인 이미지 갱신 전 이미지 설정과 해시를 `.previous`로 보존한다. 정상 RPC를
확인하지 못하면 기존 설정을 복구하고 이전 로그인 컨테이너 기동을 시도한다.
복구 기동 성공까지 보장하지 않으며 실패 기록을 확인해야 한다. 세션·키·DB를
지우지 않는다. 작업자 기동 실패는 세대 실패로 격리하며 성공한 로그인 설치는 남는다.
컨트롤러 자체 설치 중단은 자동 복구하지 않는다. 예약 작업을 멈추고 로컬 백업과
해시를 확인한 뒤 원래 `poll.sh`·`controller.sha256`를 복구한다. 서비스 볼륨이나
데이터를 삭제하는 정리 명령은 제공하지 않는다.

## 검증의 한계

자동 테스트는 요청 검증, 소스 해시, 잠금·로컬 중지, 세대 중복·실패 격리,
작업자 선택, 이미지 갱신 실패 복구를 합성 자료와 Docker/네트워크 모형으로 검증한다.
별도 실제 Docker 합성 검증은 설치·갱신과 로그인·작업자·LANraragi 흐름을 확인한다.
NAS용 일반 HTTPS 레시피의 DS718+ 실제 빌드, 실제 NAS 설치와 사이트별 로그인·다운로드는
클라우드 테스트로 확인할 수 없다. 이 결과들을 지원 완료로 표시하지 않는다.

현재 클라우드에는 NAS 관리 접속 정보와 TCP 허용이 없다. 이 채널은 NAS의
외부 방향 GitHub 조회로 배포하며 클라우드에 상태를 업로드하지 않는다.
게시 성공을 실제 NAS 적용 성공으로 보고하지 않는다. 비밀번호·쿠키를
채팅으로 받을 필요가 없고, 사용자는 설치 후 Studio 화면에서 직접 로그인한다.

2026-10-19 검증: 전체 회귀 292개, 새 채널 검사 14개 통과. 실제 클라우드
Docker 합성 실행에서 NAS 경로·호스트 UID 검사만 테스트 어댑터로 바꾸고
실제 설치기를 실행했다. 초기 연결과 이미지 갱신 RPC가 정상이고 설치 중
Studio 컨테이너 ID·시작 시각이 유지됨을 확인했다. 이후 합성 로그인·세션 저장,
실제 작업자 임대·CBZ 게시·LANraragi 색인·전체 해시 연결까지 통과했다.
테스트용 프로젝트·볼륨만 정리했으며 실제 NAS는 접근·변경하지 않았다.
