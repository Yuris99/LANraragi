# 업데이트 21 이후 새 E-Hentai 수집 확인

2026-10-25 KST. 앱 21 적용 성공과 새 실사이트 수집 성공을 구분한다.

## 실제 결과

- 기존 테스트 작품에서 정보·댓글 새 수집을 요청했다. 첫 시도는 앱의 작품별 60초 간격 검사로 사이트 요청 전에 거절됐다. 충분한 간격을 기다려 다시 요청했다.
- 두 번째 요청은 브라우저에서 JSON 대신 HTML 응답을 받아 파싱 오류가 표시됐다. 이때의 상위 HTTP 상태는 기존 UI가 보존하지 않아 확인하지 못했다.
- 같은 정상 브라우저로 실제 `/api/site-connections` JSON을 확인했다. 로그인 서비스는 연결돼 있으며 EH 최근 요청은 `saved_session / unavailable / http_status=null`, 시각은 2026-10-25 19:37:01 KST다. 메인도 동일 기록을 독립 확인했다.
- 기존 수집 시각 16:59:17, 태그 12개·댓글 7개와 작품 제목은 유지됐다. `connected`는 기존 저장 결과이며 새 수집 성공 증거가 아니다.
- 현재 서비스 5에서는 HTTP 상태 진단의 일부가 반영되지 않았다. null만으로 HTTP 이전 실패, TLS 실패나 인증 실패를 확정하지 않는다. 실제 NAS 컨테이너 로그의 현재 오류는 미확인이다.
- 다운로드·새 출처 연결·ExHentai 활성화·쿠키 재등록·접근 제한 우회는 하지 않았다. 수집 확인은 기존 출처의 표준 요청으로만 수행했다.

## 최소 수정

- `web/app.js`: JSON으로 읽을 수 없는 Studio 응답에도 HTTP 상태를 표시한다. HTML/예외 본문은 노출하지 않고, 요청을 자동 반복하지 않으며 명시적인 취소는 그대로 전달한다.
- `site_sessions.py`: 연결 실패를 예외의 타입으로만 DNS/시간 초과/TLS/인증서/연결 초기화/연결 거부/응답 디코딩/일반 네트워크 오류로 분류한다. URL·호스트·예외 메시지·쿠키를 진단에 추가하지 않는다. 연결 초기화가 TLS 중 발생했다고 추정하지 않는다.
- 최근 요청 표시는 서비스가 제공하는 고정 분류만 한국어로 표시한다. 기존 서비스 5처럼 분류가 없을 때도 작동한다. HTTP 200은 여전히 로그인 유효성 미확인으로 표시한다.
- 로컬 앱 후보 번호 22와 22개 runtime 파일 manifest를 준비한다. 공개 앱/desktop 배포 요청 JSON은 변경하지 않는다.
- 이는 관측과 오류 표시 수정이다. 실제 네트워크 접속 성공을 만드는 수정으로 보고하지 않는다.

## 메인 검토용 운영 범위

코드 후보를 커밋한 뒤 같은 Orca scratch의 `service6-diagnostics-review-plan.json`에 고정 revision·파일 해시·변경 범위·롤백안을 기록한다. 서비스 6이나 앱 22를 게시·배포하지 않았다.

서비스 5와 비교해 서비스 채널의 7개 허용 파일 중 변경되는 것은 `site_sessions.py`와 기존 앱 21의 표시/검색용 `clean_title()`가 추가된 `sources.py`다. 후자는 기존 함수 동작을 바꾸지 않는 추가 함수다. 다른 5개 서비스 파일, 의존성 및 고정 레시피는 그대로다.

승인된 후에는 기존 서비스 채널에서 login/worker 이미지 2개를 새 generation으로 빌드·교체해야 진단이 실제 NAS에 적용된다. 앱만 배포하면 login RPC의 진단 코드는 갱신되지 않는다. UID/GID·권한·볼륨·포트·키·쿠키·미디어/DB·컨트롤러·스케줄·엔진을 변경하는 제안은 포함하지 않는다.

서비스 generation 6 시도 후 코드 롤백이 필요하면, 현재 서비스 5의 정확한 revision/7개 해시를 가리키는 더 큰 generation 7 요청을 검토한다. 기존 단조 증가 검사와 attempted 상태를 삭제하거나 낮춰 우회하지 않는다. 기존 g5 이미지/소스와 세션 볼륨은 보존한다. 서비스 재생성 중 로그인 창이 종료될 수 있고 NAS 이미지 빌드 자원이 필요하므로 적용·롤백은 메인이 별도 운영 검토한다.

## 앱22 적용 이후 현재 결과와 단일 전송 단계 진단안

사용자의 추가 해결 지시 후 메인이 후보를 통합했고, 앱22·서비스6 요청을 기존 채널에 게시했다.
공개 요청 커밋은 `1ec062a5846c33838432748d6a2be062a517fa32`, 고정 소스는
`c56429a4bfd008eebfb128ab82636d5dd15589bf`다. worker도 앱22 health/status ok/백엔드 연결을 읽기 확인했다.

- 메인의 정상 갱신 1회는 Studio HTTP502로 끝났다. 새 서비스 진단은 `saved_session / unavailable / connection_reset / http_status=null`, NAS 시각 필드는 `1792935353`이다. 새 문서 파싱·저장은 실패했고 이전 수집시각·태그12·댓글7·원제목을 보존했다.
- 현재 증거는 HTTP 응답 상태를 받기 전 연결 초기화다. TLS 중 초기화인지, TCP/프록시/HTTP 헤더 단계인지 또는 상대 경로의 정책인지는 이 기록만으로 확정하지 않는다.
- DSM 관리 인증이 만료돼 메인이 사용자 로그인을 기다리고 있다. 서비스의 새 분류 동작은 확인했지만 g6 이미지 이름의 직접 확인은 남아 있다. worker는 추가 사이트 요청을 하지 않았다.
- 코드/고정 Compose에는 별도 TLS 버전·암호군 강제나 명시적인 외부 프록시 설정을 찾지 못했다. 기본 urllib는 실행 환경의 프록시 설정을 읽을 수 있으므로 실제 환경은 별도로 확인해야 한다. 설정을 바꾸지 않았다.

`diagnostics/source_transport_probe.py`는 관리 인증 복구 후 메인이 검토해 별도 login-container Python 프로세스에서 단 1회의 기존 갤러리 요청을 관찰하기 위한 후보 도구다. 아직 NAS에서 실행하지 않았다. 앱/서비스 배포 파일과 runtime manifest에는 포함되지 않으며 추가 배포가 필요하지 않다.

- 기존 서비스 사용자와 `/app` 작업 디렉터리에서 `python -B`로 실행하고, 원래 테스트 출처의 전체 URL은 프로세스의 비표시 입력으로만 전달한다. URL을 셸 명령·히스토리·채팅에 적지 않는다. 파이프 입력이면 `url` 키 1개인 JSON 한 줄만 받는다.
- 기존 세션 vault를 `readonly=True`로 열며 세션이 없으면 익명 요청으로 대체하지 않는다. 다른 provider·검색 경로·프록시·TLS 옵션을 입력받지 않는다. 키 로깅 환경이 설정돼 있으면 요청하지 않는다.
- 설치된 `source_document()`와 동일한 opener를 그대로 호출하고, 별도 프로세스 안에서 발생한 예외의 표준 모듈/함수 이름만 읽는다. 요청 방식·헤더·UA·인증서·TLS·프록시·리다이렉트 정책을 변경하지 않는다. 파일/서비스/설정을 쓰지 않는다.
- 출력은 고정 단계/HTTP/오류 분류/요청 수/런타임 버전/프록시·CA override 유무뿐이다. 예외 메시지·프레임 경로·로컬 변수·URL·쿠키·문서 본문은 출력하지 않는다. 단계 근거가 없으면 `transport_unknown`으로 남긴다. HTTP200 문서를 받아도 파싱/인증 성공으로 보고하지 않는다.
- 실제 SSL 표준 함수의 합성 프레임, 분류 불명, HTTP503, 세션 부재, 문서 수신과 파싱의 구분, 비밀값 비노출·비표시 입력·읽기 전용 vault를 포함한 검사 8개 통과. 기존 진단 11개와 함께 실행해 process-local opener 복구도 확인한다.

추가 실제 요청은 메인과 먼저 원래 경로/횟수(1회)를 공유하고 기존 간격을 지킨 뒤에만 수행한다. 인증·접근 제한·인증서 오류가 확인되면 우회/반복하지 않는다. 새로운 확정 근거 없이 전송 설정을 바꾸는 해결안은 제시하지 않는다.

메인 독립 검토에서 `getpass.getpass()`의 no-echo 실패 시 평문 fallback 가능성을 재현했다.
터미널 입력 범위의 `warnings.catch_warnings()`에서 `GetPassWarning`을 오류로 취급하도록 수정했다.
실제 표준 fallback 함수를 호출하는 합성 검사로 평문 읽기·vault·probe가 모두 호출되지 않음을 확인했고,
비공개 pipe 입력 호환과 경고 필터 복구도 확인했다. 신규 프로브 10개 + 기존 진단 11개, 총 21개 통과.
이 수정 후에도 NAS 실행·추가 사이트 요청·게시·배포는 하지 않았다.
